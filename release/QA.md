# 예상 질문과 답변 (내부 공개용)

발표·리뷰에서 받을 만한 질문 20개에 대한 답과, 그 답을 뒷받침하는 파일 위치를 정리했다.
**답하지 못하는 질문은 답하지 못한다고 적었다.** 근거 없는 답을 준비해 두면 그 자리에서 더 크게 터진다.

측정 조건은 전부 동일하다 — 데이터 `data/unified/*.jsonl`, 스코어러 `eval/span_f1.py`
(문자 오프셋 exact-match span F1, micro), 디코더 `serve/veil.py`(제약 BIOES Viterbi + 창 경계 병합 + 조사 제거).
비교 모델에도 같은 디코더를 붙였다.

## 1. "SOTA 라고 했는데, 어떤 벤치의 어떤 모델보다 어떤 metric 에서 높은가?"

**SOTA 라고 말하지 않는다.** 한국어 PII 에는 공인 리더보드가 없어 모집단을 정의할 수 없다.
말할 수 있는 범위는 이렇다.

> 동일 평가셋·동일 스코어러·동일 디코더로 비교한 **공개 모델 3종 중** 가장 높았다.

| 벤치 | n | Veil INT8 | BCCard MoAI-PF(1.4B) | Azure AI Language | FrameByFrame |
|---|---:|---:|---:|---:|---:|
| KDPII test | 4,891 | **0.9327** | 0.4533 | 0.4631 | 0.5156 |
| BCCard validation (ko) | 10,743 | **0.9825** | 0.9594 | 0.4031 | — |
| BCCard validation (en) | 3,781 | **0.9697** | 0.9653 | 0.5295 | — |
| KDPII test · 대화 단위 | 458 | **0.9420** | 0.4661 | 0.4626 | — |
| 합성 heldout v2 | 670 | **0.9652** | 0.5328 | 0.5035 | — |

영어는 2026-09-23 전까지 0.2pt 뒤졌다(0.9632 vs 0.9653). 창 분할 버그를 고치면서 0.9697 로 올라 앞섰다 — 질문 18 참조.
근거 `release/EVIDENCE.md`, 원본 JSON `release/eval_*.json` · `release/baselines/`.

## 2. "비교 모델도 같은 데이터·같은 entity schema 로 평가했나?"

같은 데이터, 같은 스코어러, 같은 디코더다. 논문 숫자를 가져다 쓰지 않았다.
BCCard 모델 카드의 자체 보고치 0.9824 는 측정 방식이 공개돼 있지 않아 비교표에 넣지 않았다.

스키마는 완전히 같지 않다. BCCard 스키마에 없는 라벨(`VEHICLE_PLATE` `SUBSCRIBER_ID` `DEVICE_SERIAL`)은
BCCard 쪽에 FN 으로 잡히므로 **"29라벨 한정" 값을 병기**했다(KDPII 0.4533 → 0.4636). 병기해도 격차는 유지된다.
Azure 는 카테고리를 우리 라벨로 매핑했고(`eval/eval_azure_pii.py`), `PersonType` `Quantity` 처럼
매핑 불가한 카테고리는 무시했다. 매핑 가능 라벨만 따로 계산한 값도 병기했다(0.4631 → 0.4741).

## 3. "학습 데이터와 테스트 데이터에 같은 문장이 섞이지 않았다는 걸 어떻게 검증했나?"

`eval/leakage_check.py` 로 세 단계 해시 비교를 했다. NFKC → 공백 제거 → 소문자, 그리고 숫자를 전부 0 으로
바꾼 템플릿 비교까지.

| 데이터 | train | test | 완전중복 | 공백무시 | 숫자마스킹 |
|---|---:|---:|---:|---:|---:|
| KDPII | 40,109 | 4,891 | 92 (1.88%) | 94 (1.92%) | 108 (2.21%) |
| BCCard | 57,851 | 14,524 | 0 | 0 | 0 |

KDPII 중복 92건은 **전부 정답 스팬이 0개**다. `알았어.` `정말 죄송합니다, 고객님.` 같은 맞장구 발화가
대화 코퍼스라 양쪽에 나온 것이다. 제거 후 재측정 결과:

| 분할 | F1 | 차이 |
|---|---:|---:|
| test 전체 | 0.9327 | — |
| 완전중복 제거(4,799행) | 0.9327 | 0.00pt |
| 템플릿중복까지 제거(4,783행) | 0.9321 | −0.05pt |

> **주의 — 이 질문에 "GPT 로 라벨 전수 검증을 했다" 고 답하면 안 된다.**
> 그건 라벨 품질(annotation quality) 이야기고, 누수(leakage)는 train/test 문장 겹침 이야기다. 다른 질문이다.

## 4. "F1 이 높은 게 모델이 좋은 게 아니라 테스트가 쉬운 것 아닌가? 사내 데이터로 평가했나?"

**사내 데이터로는 평가하지 못했다.** 이건 인정하고 간다. 대신 세 가지를 제시한다.

1. 평가셋이 셋이다 — KDPII test(공식 분할), BCCard validation, 자체 합성 heldout. 학습에 안 쓴 분할이다.
2. 같은 셋에서 상용 API(Azure)가 0.40~0.46 에 그친다. 셋이 쉬웠다면 Azure 도 높게 나왔어야 한다.
3. 난이도를 인위적으로 올린 스트레스셋을 따로 만들었다(질문 16 참조). 여기서 어디가 무너지는지 공개한다.

도입 전에는 **자체 골든셋 측정을 권한다.** 실제 상담 로그처럼 구어·오타·띄어쓰기 파괴가 섞인
분포에서는 위 수치보다 떨어진다고 보는 게 맞다.

## 5. "왜 Accuracy 가 아니라 F1 인가? 왜 micro 인가?"

**Accuracy 를 쓰면 안 되는 이유** — 토큰 분류에서 정답의 대부분은 `O`(개인정보 아님)다.
KDPII test 는 전체 토큰 중 PII 토큰이 5% 미만이다. 아무것도 안 잡는 모델이 accuracy 95% 를 받는다.
그래서 **양성(PII)만 놓고 세는** precision / recall / F1 을 쓴다.

**micro 를 쓴 이유** — micro 는 스팬 하나하나를 똑같이 한 표로 세고, macro 는 라벨별 점수를 평균한다.
"들어온 PII 100건 중 몇 건을 놓치나" 라는 운영 질문에 맞는 건 micro 다.
다만 micro 는 흔한 라벨에 가려 희귀 라벨의 실패가 안 보이므로 **macro 와 라벨별 값을 같이 낸다.**

| 데이터 | 모델 | micro F1 | macro F1 | 집계 라벨 |
|---|---|---:|---:|---:|
| KDPII test | Veil INT8 | 0.9327 | 0.9699 | 16 |
| KDPII test | BCCard 1.4B | 0.4533 | 0.5979 | 16 |
| BCCard val ko | Veil INT8 | 0.9825 | 0.9828 | 29 |

KDPII 에서 macro(0.970) > micro(0.933) 인 건 못 잡는 라벨(ORGANIZATION·PERSON·ADDRESS)이
하필 **개수가 많은** 라벨이기 때문이다. 이 차이 자체가 정보다.
macro 는 정답이 0건인 라벨(support=0)을 빼고 계산했다 — 넣으면 재현율이 정의되지 않아 평균이 왜곡된다.

**"주민번호 하나 놓치는 것과 이름 하나 놓치는 것을 같게 봐도 되나"** — 안 된다. 그래서 라벨별 표를 낸다
(`release/PER_LABEL.md`). 운영에서 라벨별 위험도에 가중치를 주고 싶다면 그건 마스킹 정책 층에서
`RRN` `CARD_NUMBER` 를 별도 취급하는 방식으로 넣는 게 맞다. 메트릭에 가중치를 섞으면 비교가 불가능해진다.

## 6. "PII 라면 F1 보다 Recall 을 우선해야 하는 것 아닌가?"

비용 구조가 비대칭인 건 맞다.

| | FP(과탐) | FN(미탐) |
|---|---|---|
| 일반 NER | 조금 불편 | 성능 하락 |
| **PII 마스킹** | 정상 정보까지 가려짐 → 가독성·업무 손실 | **개인정보 유출** |

그래서 **모델 선택 기준은 F1, 운영 튜닝 기준은 recall** 로 나눠 쓴다.

- 모델을 고를 때 F1 을 쓰는 이유: recall 만 보면 "전부 PII 라고 답하는 모델"이 1등이 된다.
- 운영에서 recall 을 올리는 장치는 따로 있다 — 디코더에 `o_bias` 파라미터를 뒀다.
  `O` 로짓에서 값을 빼 엔티티 쪽으로 기울이는 것으로, 올리면 recall↑ precision↓ 로 움직인다.
  기본값 0. 라벨별 임계값도 같은 방식으로 조정 가능하다.
- 지금 수치는 KDPII test P 0.9284 / R 0.9370 으로 **recall 이 precision 보다 높다.**
  BCCard val 도 P 0.9822 / R 0.9829 다. 의도적으로 기울인 건 아니고 학습 결과다.

## 7. "전체 F1 말고 주민번호·계좌·전화·주소·이름 각각의 recall 을 보여달라. 가장 못 잡는 게 뭔가?"

`release/PER_LABEL.md` 전문이 그 표다. 요약하면:

**KDPII test — 못 잡는 순서**

| 라벨 | n | Recall | Precision |
|---|---:|---:|---:|
| ORGANIZATION | 467 | 0.887 | 0.914 |
| PERSON | 274 | 0.912 | 0.883 |
| ADDRESS | 208 | 0.899 | 0.862 |
| RRN | 18 | 0.944 | 1.000 |
| DATE | 70 | 0.971 | 0.986 |

`PHONE` `EMAIL` `CARD_NUMBER` `ACCOUNT_NUMBER` `USER_ID` `VEHICLE_PLATE` `URL` `PASSPORT`
`DRIVER_LICENSE` `IPADDRESS` `FRN` 은 재현율 **1.000**.

**BCCard validation(ko) — 못 잡는 순서**: `GENERIC_ID` 0.905(n=2,021) · `DRIVER_LICENSE` 0.911(n=1,723) ·
`PORT` 0.933(n=163) · `ACCOUNT_NUMBER` 0.952(n=210) · `SSN` 0.958(n=1,816).

패턴이 분명하다 — **형식이 고정된 식별자는 거의 다 잡고, 문맥 판단이 필요한 이름·주소·기관명에서 놓친다.**
`GENERIC_ID` 가 낮은 것도 같은 이유다(무엇이 식별자인지가 문맥에 달려 있다).

주의: `GENERIC_ID` 와 `MACADDRESS` 는 KDPII test 에 정답이 0건이라 오탐만 집계된다. micro 에는 FP 로 반영돼 있다.

### 실패 사례를 하나 준비해 간다

"가장 못 잡는 게 뭐냐" 는 질문에는 숫자보다 실물을 보여주는 게 낫다. 재현 가능한 예다.

| 입력 | 탐지 결과 |
|---|---|
| `서울특별시 강남구 테헤란로 152` | `서울특별시 강남구 테헤란로 152` → ADDRESS ✅ |
| `서울 강남구 테헤란로 152` | `테헤란로 152` 만 ADDRESS — **`서울 강남구` 를 놓친다** |
| `주소는 서울 강남구 테헤란로 152 입니다` | `서울` + `테헤란로 152` 두 조각으로 쪼개진다 |
| `담당자 김철수(010-1234-5678), 서울 강남구 테헤란로 152` | PERSON·PHONE 만. **주소를 통째로 놓친다** |

행정구역 접미사(`특별시` `광역시`)가 붙으면 온전히 잡고, 구어체로 줄여 쓰면(`서울 강남구`) 경계가 흔들린다.
학습 데이터의 주소 표기가 정식 표기 쪽에 치우쳐 있기 때문으로 본다.
exact 0.9327 대비 partial 0.9519 의 차이(0.019)가 대부분 여기서 나온다.

운영에서 주소가 중요하면 `merge_adjacent=("ADDRESS",)` 옵션(기본 on)으로 인접 조각을 합치고,
행정구역 사전을 앞단에 두는 것을 권한다.

## 8. "주소 일부만 잡은 것도 정답 처리했나? `서울시 강남구 삼성동 123` 에서 `삼성동` 만 찾으면?"

**실패로 처리했다.** 시작·끝 문자 오프셋과 라벨이 **셋 다** 일치해야 TP 다(`key(s) = (start, end, label)`).
`삼성동` 만 잡으면 FP 1 + FN 1 이다.

참고로 겹치기만 하면 정답으로 치는 partial F1 도 같이 계산해 둔다 — KDPII test 에서
exact 0.9327 / partial 0.9519 다. **0.019 차이가 "경계를 조금 틀리는" 비율**이고, 주로 주소·기관명에서 난다.
엄격한 쪽(exact)을 대표값으로 쓴다.

## 9. "Token-level F1 인가 entity-level exact-span F1 인가?"

**entity-level exact-span F1** 이다. 토큰 단위가 아니다.

차이가 중요한 이유: `010-1234-5678` 을 토큰 6개로 보고 5개만 맞히면 **token F1 은 0.83** 이지만
실제로는 전화번호를 온전히 못 가린 것이라 **entity F1 은 0** 이다. token F1 은 PII 탐지 성능을 과대평가한다.

또 토큰 단위는 토크나이저가 다르면 비교가 안 된다. 우리는 **문자 오프셋**으로 채점하므로
BCCard(1.4B, 다른 토크나이저)·Azure(API, 토큰 개념 없음)와 같은 자로 잴 수 있다.

## 10. "한국어 전용이라는 걸 어떤 실험으로 증명했나? multilingual 보다 실제로 나은가?"

`microsoft/mdeberta-v3-base`(276M, multilingual)를 같은 데이터·같은 조건으로 학습해 비교했다.
결과는 **탈락** — 크기가 2.5배인데 성능이 따라오지 않았고, SentencePiece 의 선행공백 처리 때문에
문자 오프셋이 한 칸씩 밀려 exact match 가 0.39 까지 떨어졌다(보정 후 회복). `runs/shoot_*`, `logs/shootout*.log`.

다만 "한국어 전용" 이라는 표현은 정확하지 않다. **학습 데이터에 영어가 섞여 있고 영어도 잡는다**
(BCCard validation en 0.9697). "한국어에 맞춘" 정도가 맞는 표현이다.

## 11. "2026년에 왜 KoELECTRA-base 인가? 더 최근 인코더와 비교했나?"

|---|---:|---|---:|---|
| **koelectra-base-v3** | 110M | Apache 2.0 | **0.8789** | 채택 |
| kf-deberta-base | 185M | MIT | 0.8798 | +0.1pt 인데 INT8 245MB — 크기 목표 초과 |
| deberta-v3-base-korean | 185M | Apache 2.0 | 0.8533 | 탈락 |
| KcELECTRA-base | 110M | MIT | 하회 | 탈락 |
| mdeberta-v3-base | 276M | MIT | 오프셋 문제 | 탈락 |
| klue/roberta-base | 110M | CC-BY-SA | 미실험 | SA 조항으로 사전 제외 |

판단 기준이 성능만이 아니었다는 걸 밝힌다 — **폐쇄망 CPU 배포**가 목표라 크기와 라이선스가 같은 무게였다.
kf-deberta 가 0.1pt 높지만 INT8 245MB 는 목표(≤150MB)를 넘는다.

## 12. "왜 full fine-tuning 인가? LoRA/adapter/head-only 와 차이가 유의미했나?"

**비교 실험을 하지 않았다.** 근거 없이 "full 이 낫다" 고 답하지 않는다.

선택 이유는 성능 비교가 아니라 배포 형태였다 — 110M 짜리 인코더는 full fine-tuning 비용이
단일 GPU 수 시간이라 PEFT 로 아낄 게 없고, 최종 산출물이 **어댑터 없는 단일 ONNX 그래프**여야
폐쇄망에 그대로 올릴 수 있다. LoRA 를 쓰면 병합 단계가 하나 더 붙는다.

## 13. "주민번호·전화번호·이메일은 regex 로도 잡히는데 왜 ML 모델이 필요한가?"

**측정했다.** 정형 PII 12종에 정규식 + 체크섬(Luhn, 주민번호 가중합)을 걸고 같은 스코어러로 쟀다
(`eval/eval_regex.py`).

| 데이터 | 방식 | P | R | F1 |
|---|---|---:|---:|---:|
| KDPII test | 정규식(체크섬 on) | 0.6189 | 0.1103 | 0.1873 |
| KDPII test | 정규식(체크섬 off) | 0.6962 | 0.1272 | 0.2151 |
| KDPII test | **Veil INT8** | 0.9284 | 0.9370 | **0.9327** |

**정규식이 강한 곳은 인정하고 들어간다** — KDPII test 라벨별로 보면 정규식도 `EMAIL` 재현율 1.000,
`URL` 0.744 다. 형식이 고정된 것에는 정규식이 충분하다.

정규식이 못 하는 것이 세 가지다.

1. **대화체** — `010-1234-5678` 은 잡지만 `번호 뒷자리가 5678` `공일공에 일이삼사` 는 못 잡는다.
   KDPII 는 상담 대화 코퍼스라 이 형태가 많아 `PHONE` 정규식 재현율이 0.218 에 그친다(모델은 1.000).
2. **비정형 PII** — 이름·주소·기관명은 정규식 대상이 아니다. KDPII 정답 스팬의 **59%** 가 이 셋이다.
3. **체크섬의 역설** — 검증을 켜면 재현율이 **떨어진다**(0.127 → 0.110). 실무 데이터의 주민번호·카드번호가
   검증을 통과하지 않는 값(합성·변조·가상카드)인 경우가 있기 때문이다.

그래서 "정규식 vs 모델" 이 아니라 **정형 PII 는 정규식/검증기, 비정형 PII 는 NER** 로 나눠 설명한다.

## 14. "그러면 Regex + 사전 + NER 하이브리드가 모델 단독보다 recall 이 높지 않나?"

**높지 않았다.** 모델 결과에 겹치지 않는 정규식 결과만 더해 봤다.

| 데이터 | 모델 단독 | 정규식 ∪ 모델 |
|---|---:|---:|
| KDPII test | 0.9327 | 0.9327 (동일) |
| BCCard val ko | 0.9825 | 0.9812 (**−0.13pt**) |

이유는 단순하다 — 정규식이 잡는 자리는 모델이 이미 다 잡고 있고, 모델이 놓치는 자리(이름·주소·기관명)에는
정규식이 아예 걸리지 않는다. BCCard 에서는 정규식 오탐이 더해져 정밀도가 내려간다.

**그래도 운영에는 정규식을 붙이는 걸 권한다.** 다만 목적이 다르다 — 탐지율을 올리려는 게 아니라
`RRN` `CARD_NUMBER` 처럼 유출 시 피해가 큰 항목을 **두 경로로 확인해 감사 근거를 남기기 위해서**다.
"모델과 정규식이 둘 다 잡았다 / 한쪽만 잡았다" 가 로그에 남으면 사고 조사 때 쓸 수 있다.

## 15. "`김민수` 는 사람인데 `김민수치과` 에서는 상호명이다. 문맥 ambiguity 를 구분하나?"

구분한다. 토큰 분류 모델이라 앞뒤 문맥을 함께 보고 라벨을 정하므로, 같은 문자열이 문맥에 따라
다른 라벨로 나온다. 규칙이나 사전 매칭이라면 불가능한 부분이다.

다만 **완벽하지 않다.** 이 애매함이 정확히 못 잡는 라벨 상위 3개(ORGANIZATION 0.887 · PERSON 0.912 ·
ADDRESS 0.899)로 나타난다. `PERSON` 은 정밀도(0.883)가 재현율(0.912)보다 낮은데,
**사람 이름이 아닌 걸 사람 이름으로 잡는 경우가 더 많다**는 뜻이다.

## 16. "`공일공 일이삼사`, `010 1234 5678`, 오타, 띄어쓰기 파괴 같은 adversarial input 도 잡나?"

> **"문맥 기반이라 가능합니다" 라고 답하면 안 된다.** 측정 없이 하는 주장이고, 실제로 무너지는 구간이 있다.

정답 스팬은 그대로 두고 표면형만 바꿔 오프셋을 다시 계산한 스트레스셋으로 쟀다(`eval/make_stress.py`).

| 변형 | 예 | 원본 F1 | 변형 F1 | Δ |
|---|---|---:|---:|---:|
| 하이픈 → 점 | `010.1234.5678` | 0.9705 | 0.9686 | −0.2pt |
| 하이픈 → 공백 | `010 1234 5678` | 0.9705 | 0.9649 | −0.6pt |
| 구분자 제거 | `01012345678` | 0.9705 | 0.8967 | −7.4pt |
| 전각 숫자 | `０１０` | 0.9768 | 0.9768 | 0.0pt |
| 스팬 내부 공백 제거 | `서울강남구` | 0.9441 | 0.9623 | +1.8pt |
| **글자 사이 공백** | `홍 길 동` | 0.9431 | **0.3321** | **−61.1pt** |

**답변은 이렇게 한다.**

- 구분자 변형(점·공백·제거)에는 −0.2 ~ −7.4pt 로 버틴다.
- 전각 숫자는 **원래 못 잡았다.** 이번에 오프셋 길이를 보존하는 정규화를 넣어 고쳤다(0.33 → 0.98).
- **글자 사이에 공백을 넣은 표기는 지금도 무너진다.** 서브워드 토크나이저가 글자마다 토큰을 새로 끊어
  학습 때 본 적 없는 형태가 되기 때문이다. 이 표기를 다뤄야 하면 앞단에 정규식 룰이 필요하다.
- **`공일공 일이삼사` 같은 한글 숫자 표기는 아직 측정하지 않았다.** 학습 데이터에 이 형태가 거의 없어
  못 잡을 가능성이 높다고 본다. 측정 전에는 된다고 말하지 않는다.
- 위 변형은 전부 기계적으로 만든 것이라 실제 사용자 우회 표기의 분포와 같지 않다.

## 17. "학습하지 않은 새 PII 유형이 들어오면? Closed-set NER 의 한계는?"

**못 잡는다.** 32종 닫힌 집합이고, 새 유형은 재학습이 필요하다. 이건 구조적 한계다.

완화 장치 두 가지는 있다.

1. `GENERIC_ID` 라벨 — "식별자처럼 보이는데 어느 유형인지 모르겠는 것" 을 받는 자리다.
   완전한 해법은 아니고(BCCard val 재현율 0.905), 형식이 아주 낯설면 여기에도 안 걸린다.
2. Presidio 어댑터 — 새 유형을 정규식/사전 인식기로 얹으면 재학습 없이 추가된다.
   `PresidioVeilRecognizer` 가 모델을 하나의 `EntityRecognizer` 로 등록하므로, 다른 인식기와 나란히 돈다.

재학습 비용은 작다 — 110M 짜리라 단일 GPU 로 수 시간이다. 라벨을 늘릴 때 `labels.yaml` 1곳만 고치면
BIOES 태그(×4+O)와 전이 행렬이 따라간다.

## 18. "ELECTRA 입력 길이를 넘는 계약서·상담 transcript 는? chunk 경계에서 PII 가 잘리면?"

슬라이딩 윈도우를 쓴다. **자른 자리에서 스팬이 끊기지 않게 하는 게 핵심이고, 그건 겹침으로 해결한다.**

본문 1,200 토큰짜리 문서를 실제로 넣으면 이렇게 나뉜다(`chunk_windows`, max_len=512 · stride=128).

```
본문 토큰          0 ─────────────────────────────────────────── 1199
창 0  [CLS]   0 ──────────────── 509  [SEP]     510 토큰
창 1  [CLS]              382 ──────────────── 891  [SEP]
창 2  [CLS]                          764 ──────────────── 1199 [SEP]
                         └─ 128 겹침 ─┘   └─ 128 겹침 ─┘
```

창 0 은 509 에서 끝나지만 창 1 이 **382 부터** 시작한다. 즉 382~509 구간은 두 창이 모두 본다.
`010-1234-5678` 이 505~515 에 걸쳐 있다면 창 0 은 뒤가 잘린 채로 보지만 **창 1 은 통째로 본다.**
겹침을 128 토큰 둔 이유가 이것이다 — 한국어 PII 스팬이 128 토큰을 넘는 일은 없으므로,
어떤 스팬이든 **최소 한 창은 전체를 본다.**

같은 자리를 두 번 세면 중복 탐지가 되니, 겹침 구간을 반으로 갈라 한쪽에만 책임을 준다
(`lo = stride//2`, `hi = len - stride//2`). 결과적으로 각 창이 맡는 구간은 이렇다.

| 창 | 모델에 넣는 구간 | 결과를 채택하는 구간 |
|---|---|---|
| 창 0 | 토큰 0 ~ 509 | 0 ~ 446 |
| 창 1 | 토큰 382 ~ 891 | 445 ~ 828 |
| 창 2 | 토큰 764 ~ 1199 | 827 ~ 1199 |

**넣는 구간은 겹치고 채택하는 구간은 안 겹친다.** 창 1 은 382 부터 읽어 문맥을 확보한 상태로
445 부터의 판단만 내놓는다. 경계 바로 옆 토큰도 앞뒤 63 토큰 이상의 문맥을 보고 판단된다는 뜻이다.

마지막으로 창별 스팬을 **문자 오프셋** 기준으로 합친다(`merge_spans`). 토큰 인덱스가 아니라
원문 문자 위치로 합치므로 창이 몇 개든 결과는 원문 하나에 대한 좌표로 나온다.

| 문서 길이 | 문서 수 | P | R | F1 |
|---:|---:|---:|---:|---:|
| ~200자 | 605 | 0.9390 | 0.9495 | 0.9442 |
| ~800자 | 160 | 0.9334 | 0.9520 | 0.9426 |
| ~1,800자 | 72 | 0.9328 | 0.9526 | 0.9426 |
| ~3,000자 | 44 | 0.9291 | 0.9483 | 0.9386 |

> **이 표를 만들다가 실제 버그를 찾았다. 발표에서 이 이야기를 하는 게 낫다.**
>
> 창 분할을 토크나이저의 `return_overflowing_tokens` 에 맡기고 있었는데, 1,617 토큰 입력에
> `max_length=512, stride=128` 을 줘도 **창이 2개만** 생기고 953자 이후가 모델에 아예 들어가지 않았다.
> transformers·tokenizers 양쪽 다 같았다. 서버 입력 상한이 20,000자였으니 긴 문서에서 PII 가
> 조용히 누락되고 있었다.
>
> | 문서 길이 | 수정 전 recall | 수정 후 recall |
> |---:|---:|---:|
> | ~1,200자 | 0.759 | 0.951 |
> | ~1,800자 | 0.499 | 0.953 |
> | ~3,000자 | 0.284 | 0.948 |
>
> 창 분할을 직접 구현해 고쳤다(`veil_pii/core.py: chunk_windows`). 회귀 검사 `python -c "from veil_pii.core import _selfcheck; _selfcheck()"` (CI 에서 매번 돈다).
>
> **이 버그는 공개한 벤치 수치에도 영향을 주고 있었다.** BCCard validation 은 영어 행의 5.6%,
> 한국어 행의 4.5% 가 512 토큰을 넘는다(영어 최대 1,351 토큰). 고친 뒤 **BCCard val en 이
> 0.9632 → 0.9697 로 올랐고**, 그 결과 영어에서도 BCCard 1.4B(0.9653)를 앞서게 됐다.
> 이전 자료에 "영어에서는 0.2pt 뒤진다" 고 적혀 있다면 그건 버그가 있던 상태의 값이다.
> **KDPII test 같은 짧은 입력만 보고 있었으면 영영 못 찾았을 버그다.** 스트레스셋을 만든 값을 했다.

## 19. "latency, throughput, CPU/RAM 은? 크기가 준 것과 실제로 빨라진 것을 구분해 쟀나?"

구분해서 쟀다. `eval/bench_cpu.py`, 4/8/16 스레드, 512토큰 기준.

| 산출물 | 크기 | 4스레드 512tok | 8스레드 | 16스레드 | KDPII F1 |
|---|---:|---:|---:|---:|---:|
| fp32 ONNX | 450MB | 273.6ms | 168.5ms | 117.8ms | 0.9339 |
| **weight-only INT8 + fp16 emb (공개본)** | **143MB** | 236.6ms | 145.9ms | 107.9ms | **0.9327** |
| weight-only INT4 (실험) | 100MB | 260.8ms | 175.0ms | 118.9ms | 0.9321 |
| dynamic INT8 (activation 도 INT8) | 114MB | **95.1ms** | 60.8ms | 57.9ms | **0.8960** |

**핵심은 이것이다 — 크기는 68% 줄었지만 속도는 13.5% 밖에 안 빨라졌다.**

이유가 명확하다. 우리가 쓴 건 **weight-only 양자화**다. 가중치만 INT8 로 저장하고 activation 은 fp32 로
둔다. 런타임이 INT8 가중치를 연산 직전에 fp32 로 되돌려(dequantize) fp32 activation 과 곱하므로,
**메모리와 파일 크기는 줄지만 실제 GEMM 은 여전히 부동소수점 연산**이다.

진짜 INT8 GEMM(가중치·activation 둘 다 INT8, 누산 INT32)을 쓰면 95.1ms 로 2.5배 빨라진다.
하지만 **F1 이 0.9339 → 0.8960 으로 3.8pt 떨어진다.** 재현율이 0.934 → 0.850 으로 특히 크게 빠진다.
Transformer 인코더의 activation 분포에 이상치가 있어 INT8 [-128, 127] 구간으로 뭉개면 정보가 날아가기 때문이다.
FFN 만, attention 만, 앞 2개 층 제외 등 부분 적용도 다 해 봤고(`runs/final_v4_full/hybrid/hybrid.json`),
손실을 1pt 안쪽으로 줄이면서 속도를 얻는 조합은 찾지 못했다.

**그래서 크기·정확도를 택하고 속도를 포기했다.** 목표였던 4 vCPU 512토큰 40ms 는 미달이다.
이건 `release/EVIDENCE.md` 의 "주장하지 않는 것" 에 적어 두었다.

실제 서비스 입력은 512토큰보다 짧은 경우가 많다 — 128토큰이면 4스레드 60.8ms 다.
KDPII test 전체(4,891행) 처리에 8스레드 15.9초, 행당 3.26ms(평균 25자 발화 기준).

## 20. "recall 이 100% 가 아니면 이 모델을 통과한 텍스트에 개인정보가 없다고 보장할 수 없지 않나? 운영에서 residual risk 를 어떻게 처리하나?"

**보장하지 않는다.** KDPII test 기준 스팬 1,604개 중 **101개를 놓친다.**
단일 모델을 guardrail 로 단독 배치하면 안 된다.

> **"Langfuse·Phoenix 같은 모니터링 도구로 사후 처리한다" 는 답은 약하다.**
> 사후 관측은 이미 나간 개인정보를 되돌리지 못한다. 이건 **탐지**지 **차단**이 아니다.

방어를 층으로 쌓는 게 맞는 답이다.

```
사용자 입력
    ↓
① 정규식 / 검증기      ← 형식 고정 PII(주민번호·카드·계좌·이메일). 체크섬으로 확신도 부여
    ↓
② Veil NER (이 모델)   ← 문맥 의존 PII(이름·주소·기관명). 32종
    ↓
③ 후처리 / 검증        ← BIOES Viterbi 로 불가능한 태그열 차단, 조사 제거, 창 경계 병합
    ↓
④ 마스킹 정책          ← 라벨별 차등: RRN·CARD 는 전체 치환, PERSON 은 부분 마스킹 등
    ↓
⑤ 감사 로그            ← /detect 의 summary 를 남겨 무엇을 왜 가렸는지 추적
    ↓
  LLM 호출
    ↓
⑥ 출력단 재검사        ← LLM 응답에도 같은 파이프라인을 한 번 더
    ↓
⑦ 사후 모니터링        ← Langfuse·Phoenix. 여기는 마지막 층이지 1층이 아니다
```

각 층이 다른 실패 유형을 잡는다. 모델이 놓치는 `01012345678` 은 ①이 잡고, ①이 못 잡는
`김민수 고객님` 은 ②가 잡는다. 둘 다 놓치는 `홍 길 동` 은 현재 구조에서 못 잡는다 —
이건 알려진 구멍으로 두고, 해당 표기가 문제되는 도메인이면 ①에 룰을 추가해야 한다.

**어디에 쓸지에 따라 요구 수준이 다르다는 것도 같이 말한다.**

| 용도 | 잔여 위험 감내 | 이 모델 단독 |
|---|---|---|
| 사내 LLM 프롬프트 전처리 | 중 | 층 ①③④⑤ 와 함께면 가능 |
| 로그·데이터셋 비식별화 | 중 | 샘플 검수 병행 전제로 가능 |
| 대외 공개 문서 비식별화 | 낮음 | **단독 불가** — 사람 검수 필수 |
| 법적 비식별 조치 증빙 | 매우 낮음 | **단독 불가** |
