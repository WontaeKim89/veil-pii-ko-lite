Veil-PII-Ko-Lite 결과 보고

110M 한국어 인코더로 만든 개인정보(PII) 탐지 NER 모델. 공개 벤치마크에서 BCCard MoAI-Privacy-Filter(1.4B)와 정면 비교하고, INT8 ONNX 로 CPU 에서 돌린다.

백본 monologg/koelectra-base-v3-discriminator (Apache 2.0)라벨 32종 · BIOES 129 클래스학습 H100 ×1 · 6 epoch · ~40분평가 3축 + INT8/INT4Xeon 8480C CPU 벤치

110M 짜리 KoELECTRA 로 만든 Veil-PII-Ko-Lite v4 가 세 공개 벤치 전부에서 BCCard MoAI-Privacy-Filter(1.4B)를 같은 스코어러로 앞선다. KDPII test exact F1 0.9333(BCCard 0.4533), BCCard 자체 validation 0.9820(BCCard 0.9589), 합성 heldout 0.9634(BCCard 0.5317). 영어(BCCard val en)도 0.9700. KDPII 로 학습한 공개 모델 FrameByFrame/privacy-filter-korean(자체 보고 0.848)은 공식 test 에서 0.5156(자기 9라벨 한정 0.6824) — 같은 9라벨로 좁힌 v4 는 0.9383.

크기 목표(≤150MB)는 weight-only INT8 + fp16 임베딩 = 143MB, 정확도 무손실(KDPII 0.9335 / BCCard 0.9818)로 달성했다. INT4 는 100MB 에 0.9321. 단 CPU 지연 목표(4 vCPU 512토큰 ≤40ms)는 미달 — 실제 문장 512토큰 기준 fp32 274ms, weight-only INT8 237ms(크기만 줄고 속도 이득 없음), 동적 INT8 은 95ms 지만 −7pt 손실. 128토큰(일반 문장) 기준으로는 INT8 61ms · 16스레드 33ms. 처음 보고했던 '3.6ms'는 더미 입력이 [UNK] 로 축약된 벤치 버그였고, 이 문서는 바로잡은 수치만 쓴다.

가장 값진 발견은 벤치 밖에 있었다. v3b 는 벤치 최고점이었지만 김철수·홍길동·이영희를 개인정보로 잡지 못했다 — LLM 이 만든 템플릿에 이 '더미 이름'이 플레이스홀더 없이 1,300회 들어가 O 로 학습된 데이터 결함. v4 는 이를 고쳐 프로브 17문장 전부 정답이며 벤치는 v3b 와 동률(±0.2pt)이다. 최종 = v4. 외부 공개 모델은 v4 하나 — safetensors(정식) + INT8 ONNX(배포용). 실험 변형(INT4·동적 INT8·v3b)은 공개하지 않는다.

벤치마크 결과

같은 스코어러(문자 오프셋 exact-match span F1, micro)로 모든 모델을 잰 수치. exact 는 시작·끝·라벨이 모두 일치해야 정답, partial 은 같은 라벨로 겹치기만 하면 정답. 베이스라인의 '자기 라벨 한정' 열은 그 모델이 아예 모르는 라벨(예: BCCard 에 없는 VEHICLE_PLATE)을 제외하고 다시 계산한 값이다.

데이터 — 무엇을 쓰고 무엇을 버렸나

공개 데이터 두 종을 받아 포맷 검증기(주민번호·전화·카드·면허·여권·사업자번호 등 21종 규칙)로 행 단위 감사를 했다. 검증기는 '형태만' 본다 — 합성 데이터라 Luhn·체크섬은 요구하지 않았다(BCCard·KDPII 모두 체크섬 미충족).

BCCard/privacy-filter-openpii-masking 72.4k행(ko 42,963 / en 14,888, CC-BY-4.0). 세 출처 중 openpii-1.5m-ko(ai4privacy 한국어 번역본 21k)는 35% 행이 불량이었다: 운전면허 라벨의 61% 가 OW4SB7XAR4 같은 랜덤 대문자열, 이름의 13% 가 선임Blattnig·Celissa장 같은 혼합문자. 반면 perturbation 13k행은 1% 불량으로 깨끗했고, 자체 합성 11k 는 라벨링 가이드 문장을 필러로 쓴 부자연스러운 텍스트였다. 이 감사가 BCCard 모델이 스스로 약하다고 밝힌 ACCOUNT_NUMBER·ZIPCODE·PORT 의 원인을 설명한다 — '랜덤 문자열 = 식별자'를 배운 것이다.KDPII(고려대, CC-BY-4.0) 40k 문장·3,664 대화. 실제 구어체라 최고 품질이지만 문장이 평균 25자로 짧다 → 대화 단위로 이어 붙인 장문 표본(3,664건)을 별도로 만들었다. 33개 라벨 중 절반(키·몸무게·혈액형·종교 등)은 우리 스키마 밖이라 O 로 두었고, 카드·계좌 스팬에 붙은 은행명은 숫자 구간으로 정규화해 BCCard 관행과 맞췄다.합성: VM 의 vLLM(gemma-4-12b-it)과 Azure OpenAI(gpt-5.2)에 20개 장르 × 7개 문체로 플레이스홀더 템플릿 ~4,700개를 만들게 하고, 한국 포맷을 정확히 지키는 생성기(주민번호는 2020-10 전후 분포, 카드는 Luhn, 사업자번호 체크섬, 차량번호·가입번호·단말 S/N)로 채웠다. 정답 라벨이 생성 시점에 확정되므로 교사 모델 증류보다 라벨이 정확하다. 주문번호·상품코드·버전·금액 같은 hard-negative 를 정답과 같은 빈도로 섞었다. heldout 은 템플릿 텍스트 해시로 고정해 버전이 바뀌어도 누출되지 않는다.

두 벌의 학습셋: clean(BCCard 불량 행 제외) / full(전부). 어느 쪽이 나은지는 가정하지 않고 둘 다 학습해 비교했다.

모델 — 왜 KoELECTRA 인가

같은 데이터(clean)·같은 하이퍼파라미터·2 epoch 로 백본 shootout 을 했다: KoELECTRA-v3(110M, Apache) / KcELECTRA(110M, MIT) / mDeBERTa-v3(276M, MIT) / kf-deberta(카카오뱅크, MIT) / deberta-v3-base-korean(Apache). 결과는 벤치 표 참조. KoELECTRA 가 KDPII 에서 가장 높았고 가장 작았다.

구조: 토큰 분류 헤드 + 제약 BIOES Viterbi(불가능한 전이 차단) + 슬라이딩 윈도우 512/128 + 창 경계 스팬 병합. SentencePiece 계열의 선행공백 오프셋은 스팬 양끝 공백 제거로 보정했다(이 보정 없이는 mDeBERTa 의 exact F1 이 0.39 로 나온다 — partial 0.93 과의 차이가 순수 경계 문제였다).

라벨 32종 = BCCard 29종 + VEHICLE_PLATE(KDPII 실데이터) + SUBSCRIBER_ID + DEVICE_SERIAL. 모델은 전부 혼자 책임진다 — 공개 자산에는 룰이 따라가지 않는다.

동적 양자화의 손실은 정밀도가 아니라 재현율(0.86→0.68)에서 났다 — 활성값 양자화 오차가 O 클래스 쪽으로 편향된다. O 로짓 보정으로 +1pt 회복이 한계였다. BCCard 가 택한 weight-only(활성값 fp32) 방식이 정확도를 지키지만 ORT 의 MatMulNBits 8bit 커널이 이 CPU 에서 속도 이득을 주지 못했다. 민감도 탐색(KDPII 1.5k 부분셋, fp32 0.9407): 손실의 출처는 FFN이다 — FFN 만 동적 양자화하면 0.9020(−3.9pt), 어텐션만 하면 0.9388(−0.2pt). 어텐션은 INT8 활성값을 견디지만 FFN(GELU 뒤 넓은 활성 범위)은 못 견딘다. FFN 이 FLOPs 의 2/3 라 어텐션만 양자화한 변형은 213ms 로 속도 이득이 작다. 속도가 필요하면 남는 카드는 스레드(16스레드 108ms)거나, FFN 을 SmoothQuant/QAT 로 다시 학습하는 것이다 — 이번 범위 밖.

정직하게 적어야 할 것

BCCard 모델의 KDPII 점수는 우리 스코어러·우리 디코더로 잰 값이다. 레포에 디코더가 없어 제약 Viterbi 를 우리 구현으로 적용했고 viterbi_calibration.json(포맷 미공개)은 쓰지 못했다. 그래도 partial F1 까지 낮은 것은 디코딩 문제가 아니라 KDPII 분포(구어체·짧은 문장·닉네임)를 못 보는 것이다.KDPII 와 BCCard 의 라벨 관행이 다르다. KDPII 는 생년월일만 DATE, BCCard 는 모든 날짜가 DATE. KDPII 의 장소명(교회·식당·도시)은 ADDRESS 로, 동아리명은 ORGANIZATION 으로 매핑했다. 이 불일치가 KDPII DATE·ADDRESS·ORGANIZATION 의 상한을 만든다 — 모델 문제라기보다 라벨 정의 문제다.사람이 라벨링한 고객 도메인 골든셋은 아직 없다. 공개 실데이터(KDPII test)와 BCCard validation, 합성 heldout 으로 대신했다. 프로덕션 도입 전 P0(500~1,000건 라벨링)은 그대로 남는 숙제다.BCCard validation split 은 BCCard 학습 분포다. 우리도 같은 분포로 학습했으니 공정하지만, 그 분포 자체가 35% 불량이라는 점은 위에 적은 대로다. clean/full 절제가 이 트레이드오프를 숫자로 보여준다.CPU 지연 목표는 미달이다. 512 토큰 문서를 4 vCPU 에서 40ms 안에 처리하는 정확한 변형은 없다. 짧은 문장(≤128 토큰)은 61ms, 16스레드면 33ms. 첫 보고의 3.6ms 는 벤치 입력 오류였다.FrameByFrame 비교는 우리 매핑에 의존한다. 그 모델의 9개 라벨(private_person/address/phone/email/date/url, account_number, personal_handle, ip_address)을 우리 스키마로 매핑해 같은 스코어러로 쟀다. KDPII 의 은행명 포함 계좌 스팬을 그 모델은 전혀 못 잡았고(ACCOUNT 0.00), 주소 재현율 0.45 가 격차의 대부분이다. 자체 보고 0.848 은 본인이 나눈 검증 분할 값으로, 공식 test 와 분할이 다르다.

재현

주장 재현 패키지 — release/EVIDENCE.md(주장별 근거표·측정 조건·주장하지 않는 것) + scripts/reproduce_claims.sh(공개 데이터 다운로드 → Veil-PII-Ko-Lite INT8/fp32 · BCCard 베이스라인 5개 평가 → 표 출력, CPU 8스레드 약 40분). 외부인이 이 한 명령으로 위 표의 핵심 수치를 다시 계산할 수 있다.
pip install -r scripts/requirements-repro.txt
bash scripts/reproduce_claims.sh release   # ① Veil-PII-Ko-Lite INT8 3벤치 ② fp32(무손실 확인) ③ BCCard 동일조건

전체 파이프라인 재현: 

python data/audit.py            # 품질 감사
bash scripts/build_data.sh      # 템플릿 채우기 → train_clean/full
bash scripts/run_final.sh       # 학습 → 평가 → ONNX
python eval/report.py           # 비교표

모든 벤치 수치는 runs/**/eval_*.json 에 per-entity 까지 저장돼 있고 eval/report.py 가 표를 재생성한다.
